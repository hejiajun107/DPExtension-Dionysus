# 鼠标滚轮缩放战场 —— 调研与实施方案

调研方式：IDA 静态逆向 `gamemd.exe`（YR 1.001）+ 项目代码阅读 + Phobos 源码检索。
本文件只给结论与方案，不含实现代码。

---

## 0. 已拍板的三个前提

| 决策 | 结论 |
|---|---|
| 滚轮冲突 | **鼠标在战场区域内才缩放**；鼠标在侧栏/UI 上时仍走原版侧栏滚动 |
| 缩放范围 | **必须双向**，默认 `[0.66, 2.0]`（可配置档 `0.5 / 0.66 / 0.8`），即既要放大也要缩小看更大范围 |
| 缩放中心 | **鼠标位置**（滚轮指哪缩哪） |

双向 + 鼠标锚点，意味着不能靠"整幅裁切放大"的取巧做法，必须让引擎真的渲染更大范围。

## 1. 关键事实（IDA 确认，含上一版的更正）

### 1.1 引擎没有现成的战术缩放

- TacticalClass vtable（`0x7E608C`，24 项）全是桩函数；投影是硬编码立即数 `60/30`（`0x6D1EB0`，另有内联副本 `0x6D96C8~0x6D96D4`、`0x6D214F`、`0x6D1F95`）。
- `[General] ZoomInFactor`（RulesClass `+0x550`）**只被 World Domination Tour 的 TAction 49/50 消费**，不是战术缩放开关。

### 1.2 世界画在 Tile 上，Composite 只装战术区

| 表面 | 全局 | 用途 |
|---|---|---|
| `Tile` | `0x8872FC` | **世界层真正的绘制目标** |
| `Composite` | `0x88731C` | 合成结果 + 上屏源（只含战术区，**不含侧栏**） |
| `Sidebar` | `0x887300` | 侧栏，独立表面、独立上屏（`0x4F451B`） |
| `Primary` | `0x887308` | 最终屏幕 |
| `Temp` | `0x887314` | "当前绘制目标"别名，渲染前后保存/恢复 |

- 世界层：`sub_6D3D10`（`0x6D3D10`）里 `Temp = Tile` → `Tile->Lock()` → 画 8 个图层 → `Unlock()` → `Temp = Composite` → `Composite->CopyFromPart(&ViewBounds, Tile, &ViewBounds, 1, 0)`（`0x6D45D8`）。
- 每帧 `n2==0` 时 **Tile 与 Composite 两个全局会整体交换**（`0x6D4057~0x6D4076`），所以**两者必须永远同尺寸**。
- 侧栏、消息栏、鼠标、我们自己的 UI 都是 Composite 上屏**之后**画在 Primary 上的 → 缩放 Composite **不会**缩放它们。

### 1.3 `Tactical+0xC0` 是引擎自带的"最终上屏缩放因子"（重要）

- 位置 `0x887324->0xC0`，double，构造时 = `1.0`（`0x6D1C42/0x6D1C60`），只有 `sub_4F4780` 读它。
- destRect **恒为 Composite 整幅**，srcRect 随它变：
  - `= 1.0`：src = `(0,0,W,H)` → 1:1
  - `> 1.0`：src = Composite 中心 `W/s × H/s` → **居中裁剪放大**（这就是免费放大）
  - `< 1.0`：src 越出表面（`fdiv` 后为负/超出），DDraw 会裁剪 → 只是"整幅缩到中间 + 黑边"，**不能缩小视野**
- 结论：`+0xC0` 可用于放大方向（零表面改造）；不能用于缩小。
- 注意写者不止构造函数：WDT 的 TAction 49/50（`0x6DEECA/0x6DEF3A/0x6E2872/0x6E28E5`）会临时改写它再恢复 1.0。冲突面很小，但过场期间不要叠加。

### 1.4 视野由 ViewBounds 决定，"画多少格"确实跟着它走

- `sub_6D8B30`（`0x6D8B30`）：`+0xB0 = 相机中心X − ViewBounds.W/2`，`+0xB4 = 相机中心Y − ViewBounds.H/2`，并重算起始 cell 与 cell 网格尺寸。
- `sub_6D7560`（`0x6D7560`）：列数 = `rect.Width/60 + 4`、行数 = `rect.Height/15 + 17`；起点 = `(origin + rect.XY − ViewBounds.XY)` 反算 cell。
- `sub_6D2140`（`0x6D2140`）：`screen = iso(world) − (+0xB0/+0xB4)`，**不再加 ViewBounds**（已被吸收进原点）。
- 所以把 ViewBounds 放大到 `W/z × H/z`（保持相机中心不变），世界会自然以中心为原点、按 `1/z` 的跨度画在大表面上，中心精确落在表面正中。
- **坑**：渲染侧还有一份 ViewBounds 缓存 `xmmword_B0CE28`，写者只有 `sub_6D1A40`（清零）和 `sub_6D5F60`（`0x6D5F6C~0x6D5F87`）。只改 `0x886FA0` 不改缓存 → 原点/cell 数/cull 全用旧值，必然错位。

### 1.5 上一版的一处判断是错的

`sub_6D9A50(ViewBounds.X-64, Y-64, W+128, H+128)` **不是**"画一块更大的区域"，而是"预登记建筑脏矩形"（滚动时只重画露出的边条）。所以不能借它做超采样，必须走真扩容。

### 1.6 滚轮链路

- 主 WndProc `sub_7775C0`：`0x77795A` 判 `WM_MOUSEWHEEL(0x20A)`，`0x777985` 按 wParam 符号选 `"SidebarUp"/"SidebarDown"`，经 `sub_533F50`（热键派发器）执行 → 目前就是侧栏滚动。
- 滚轮**不经过 MouseClass**（`sub_6930A0` 的 switch 只有 `0x201/0x202/0x204/0x205/0x215`），现有三个鼠标 hook 拿不到，必须新增 WndProc 侧 hook。

## 2. 方案

核心思路：**按 `z` 缩放，把"要画的世界跨度"设成 `W/z × H/z`，画到一张足够大的表面上，再缩回屏幕。**

- `z > 1`（放大）：跨度为 `W/z`，引擎按原像素密度画进较小的区域，最后放大上屏 → 必然 upscale。
- `z < 1`（缩小）：跨度为 `W/z > W`，引擎画更多格子，最后缩小上屏 → **超采样，缩小后反而更清晰**。

### 2.1 关键设计：表面固定一张"最大尺寸"，只用 ViewBounds 做缩放

不要在每次滚轮时重建表面（`Set_View_Dimensions` 每次都会析构/新建 ZBuffer、ABuffer，还会按新宽度重排消息栏，太重）。

做法：
1. 启动/分辨率变化时，一次性把 **Composite 和 Tile 建成 `1.5W × 1.5H`**（即支持到 `z = 0.66` 的最大超采样，推导见第 5 节），ZBuffer/ABuffer 也一次性按同尺寸建好。
2. 缩放时**只改 `DSurface::ViewBounds`** 为 `{0, 0, W/z, H/z}`（`z ∈ [0.66, 2.0]`，因此 `W/z ≤ 1.5W`，永远不超过表面）。
3. 同时刷新缓存 `xmmword_B0CE28`（调 `sub_6D5F60`）并重算原点（`sub_6D8B30`）。
4. 最终上屏改成"从 Composite 的 `ViewBounds` 区域拉伸 Blt 到 Primary 的战术区 `W×H`"。

这样滚轮只是改一个矩形 + 一次缓存刷新，没有内存分配，帧内开销可忽略。
（这条是本次方案的关键优化点，**需要阶段 0 实测验证**，见 3.1。）

### 2.2 两个方向的实现分工

| 方向 | 表面 | ViewBounds | 上屏 |
|---|---|---|---|
| `z >= 1`（放大） | 保持 `1.5W×1.5H` 不变 | `{0,0,W/z,H/z}` | `srcRect = ViewBounds` → dest `W×H`（放大拉伸） |
| `z < 1`（缩小） | 同上 | `{0,0,W/z,H/z}`（> W，最大 1.5W） | 同上（缩小拉伸，超采样） |

两条路径其实是同一套代码，只是 `ViewBounds` 落在不同大小。`z == 1` 时 `srcRect == W×H`，等价于原版 1:1。

> 备选（更省事的放大）：`z >= 1` 时保持 ViewBounds 原样、直接写 `Tactical+0xC0 = z` 让引擎自己居中裁剪放大。这样放大方向零风险、可先独立交付（见里程碑 M1）。缺点是缩放跨过 1.0 时两套机制要切换，首版建议**统一走超采样**，`+0xC0` 强制保持 1.0。

### 2.3 鼠标锚点

缩放前后保持鼠标下的世界点不动：

```
pc = 屏幕中心（战术区中心）
p  = 鼠标客户区坐标
z' = 新缩放
相机中心平移 = (p − pc) × (1/z − 1/z')   // 叠加到 Tactical+0xD64/+0xD68
```

写回后调 `sub_6D8B30`（`0x6D8B30`）重算原点。因为 `z` 是连续量，`0xD64/0xD68` 与 `0xD74/0xD78`（目标值）**要同时写**，否则 `sub_6D2540` 的每帧平滑会把中心拉回去。

### 2.4 拾取逆变换（不做就点不中）

`sub_692300`（`0x692300`，6 参数，`retn 18h`）是统一的拾取漏斗，内部两行做 `crd = ViewBounds.XY + *pixel`。在上屏被拉伸后，进入它的屏幕像素需要先还原：

```
p' = pc + (p − pc) × z
```

即 `z > 1` 时把鼠标向外推、`z < 1` 时向内收。注入点放在 `0x69236B` 之前（两行），7 个调用点一次全中。

另外有 3 处直接调 `sub_6D2280` 的路径（`sub_4AAC10` / `sub_4AE4F0` / `sub_4FB0E0`）也要乘 `z`，否则地图落点提示、坐标显示会偏。

### 2.5 相机 clamp 会限制缩小幅度

`sub_6D8640`（`0x6D8640`）clamp 相机中心，边界公式里用了 ViewBounds 的 W/H：

```
minX = Wv/2 + 30*(2*VisibleRect.X − MapRect.Width)
maxX = minX + 60*VisibleRect.Width − Wv
```

`VisibleRect` 是地图 `[Map] LocalSize`（可玩区域 cells）。`Wv` 越大（缩得越小），可平移范围越小；当 `Wv ≥ 60*VisibleRect.Width` 时 `min > max`，相机会被钉在边界 → **中心缩放失效**。

对策（纯注入，不 patch）：
- 缩放帧在 `sub_6D5F60` 之后**覆盖** `+0xD64/0xD68/+0xD74/0xD78` 为锚定后的中心，再调 `sub_6D8B30`。
- 或把 `z` 下限收敛到安全值（60 格地图、1280 宽时约 `z ≥ 0.36`，取 **0.66** 有接近一倍余量）。
- 首版：`z ∈ [0.66, 2.0]` 并采用"事后覆盖"，超出地图时自然贴边即可，不做特殊处理。

### 2.6 不会缩放的部分

侧栏、消息栏、工具栏、鼠标指针、我方 UI 面板、弧形刻度盘 —— 全部在 Composite 上屏后画在 Primary 上（`0x4F4547~0x4F4583`），天然不受影响。唯一会跟着缩的是战术覆盖层（选择框/血条/单位血条，`n2==2` 画进 Composite），这是**正确**行为，且与拾取逆变换一致。

## 3. 实施路径（三个可独立验收的里程碑）

### M0：验证（不写业务代码）

1. ~~**表面固定大尺寸是否成立**~~ **已验证（静态）**：`Tile`/`Composite` 在 `Tile->Lock`(0x6D4117)~`Unlock`(0x6D455E) 之间**没有任何整幅清屏**，8 个图层的矩形在传入前都先与 `ViewBounds` 求交（0x6D42B0–0x6D4308 的 `Drawing__Intersect`）。所以表面放大到 1.5 倍**不会带来恒定的清屏开销**，`z=1` 仍是零额外成本。
   - **ZBuffer/ABuffer 必须同步扩到 1.5 倍**：索引用 buffer 自身 `Width`（0x7BD0BC `+= 2*Width`），但写入坐标来自 `ViewBounds`，而 `DSurface::Lock`(0x4BAE13) 只判下界、无 X/Y 上界检查，`0x7BD00B` 仅一次 `BufferEnd` 回卷 —— `ViewBounds > buffer` 会让 0x7BD03F 的 `memset` 写出堆外。反过来说 **buffer ≥ ViewBounds 是安全的**，所以"固定 1.5 倍 buffer + 动态 ViewBounds"成立。
   - 代价：强制全重绘帧（0x6D3F8F，Z 用 0x7BCF50 / A 用 0x4112D0）按 buffer 自身尺寸整幅填充，1.5 倍 buffer 时是 2.25 倍面积；滚动帧（0x6D401B / 0x6D4042）只搬移并填暴露条带，不受影响。
2. ~~**每帧清屏范围**~~ **已验证**：`Tile`/`Composite` 无整幅清屏；唯一整幅填充是 Z/ABuffer 的全重绘帧。另外 `sub_6D9A50` **不是清屏**，而是"视野内建筑脏矩形预登记 + 清 `NeedsRedraw`"（0x6D9AF2 相交测试 → 0x6D9B1A 清零），借不到超采样。
3. **上屏替换**：hook `0x4F4596`（`call [edx+44h]`，即 `sub_4F4780` 的调用点）或 `0x4F4780` 入口，改成从 Composite 的 `ViewBounds` 区域拉伸 Blt 到 Primary 战术区。
   - 要确认两件事：一是 `dwUnk = 0`（不落软件 blitter）；二是**驱动是否真的用硬件做非 1:1 拉伸**（老驱动可能回落到软件模拟，那样每帧 1280×720 软件缩放会很痛）。
4. **滚轮消费**：确认 `sub_7775C0` 的 `retn` 地址（用于吞掉消息后直接返回），以及 `0x777985` 处栈上能否拿到 `wParam`/`lParam`。
5. **`+0xC0` 现状**：确认正常游戏流程里它恒为 1.0（除 WDT 过场）。

验收：一张静态画面在新尺寸下像素级正确，UI/侧栏/鼠标完全不变。

### M1：滚轮链路 + 弧形刻度盘（不依赖缩放核心，可先做）

- `GeneralHooks/MouseWheelHook.cs`：
  - hook `0x777985`，读 delta；
  - 用 `GetCursorPos` + `ScreenToClient(hWnd)` 取客户区坐标，判断是否落在 `ViewBounds` 内（在侧栏/UI 上则**放行**原版逻辑）；
  - 命中战场则广播 `MouseWheelEvent` 并吞掉消息（跳过 `sub_533F50` 的 `SidebarUp/Down`）。
- 扩展 `Projects/Extension/EventSystems/MouseEventSystem.cs`：新增 `MouseWheelEvent` + `MouseWheelEventArgs { int Delta; int X; int Y; bool InField; }`。
- `Extension.UI/ZoomIndicator.cs`：顶部弧形刻度盘（见第 4 节）。
- 注意项目既有规则：默认"只观察不跳转"，需要消费时用"跳到该函数自身 `retn`"的写法，**不要写 `R->ESP`**（POPAD 不恢复 ESP）。

验收：滚轮只在战场内响应；侧栏滚轮行为完全不变；刻度盘能跟随手动设定的数值显示。

### M2：缩放核心

- `Extension.UI/ZoomController.cs`：
  - 维护 `Target` / `Current`（缓动，约 120ms 按帧插值）；
  - 范围 `[0.66, 2.0]`（默认档，可配置为 `0.5 / 0.8`），每格滚轮 `0.1`；
  - 输出：`ViewBounds = {0,0,W/z,H/z}`、鼠标锚点后的相机中心。
- 每帧在 `0x4F4480`（`DrawOnTop` 真入口，此时还没读 Composite）：
  1. `z` 有变化才动作（`z` 不变时零开销）；
  2. 写 `ViewBounds`，调 `sub_6D5F60` 刷缓存；
  3. 覆盖相机中心（鼠标锚点 + 绕开 clamp），调 `sub_6D8B30`；
  4. 强制 `Tactical+0xC0 = 1.0`。
- `sub_692300` 内补拾取逆变换（2.4），并处理 3 个 `sub_6D2280` 直连调用者。
- 场景切换 / 分辨率变化时恢复 `ViewBounds` 原值并复位 `z = 1`（`ScenarioClearClassesEvent`）。

验收：
- 缩小后可见范围成比例变大且**更清晰**（真超采样），放大可用；
- 鼠标指向的格子缩放前后不跳；
- 边缘 clamp 行为可预期；
- 反复缩放无内存增长、无花屏、无崩溃；
- `z` 回 1.0 后与原版完全一致。

## 4. 顶部弧形刻度盘

- **位置**：屏幕顶部居中（`x = ViewBounds.X + ViewBounds.Width/2`，`y ≈ ViewBounds.Y + 46`），画在 Primary 上（我方 UI 阶段），不受缩放影响。
- **形态**：向上开口的半圆弧，半径约 72px，角度 `−60° ~ +60°`（以竖直向上为 0°），每 `7.5°` 一根刻度，共 17 根。
  - 中点（0°）为主刻度，最长（14px）；±45° 与 ±60° 为次长（10px）；其余 6px。
  - 当前 `z` 对应的刻度用亮色（白 / 浅青），其余用暗灰（`64,64,64`）。
  - 弧线本身用 2 段折线近似（`Surface.DrawLine`，vtable 12），或只在两端点画端点标记，避免逐像素画弧。
- **数值**：刻度盘中心下方一行 `1.0x` 文本（沿用项目现有 `Fancy_Text_Print_Wide` 封装）。
- **映射**：`index = 8 + 8 * log2(z)`，`z=1 → 8`、`z=2 → 16`。
  - 用 log 而非线性，是因为放大/缩小在**视野跨度**上的手感应该对称（`z` 与 `1/z` 等距），线性映射会让放大一侧挤在一起。
  - `z` 下限 `0.66` 对应 `index ≈ 3`，所以最左 3 根刻度画成**禁用态**（更暗、不可达），暗示还能再往下但有性能代价。
- **出现/消失**：`z` 变化时出现，保持 900ms 后 400ms 内淡出。
  - 引擎表面无 alpha 通道，淡出用"颜色向背景插值 + 每帧减少可见刻度数量"模拟；
  - 复用 `TutorialPanel` 里那套 `Environment.TickCount` + 每帧现算进度的做法（无 Timer、无线程）。
- **联动**：只在 `z` 真正变化的那一帧重置计时，缓动期间不重复重置。

## 5. 性能预算（为什么下限取 0.66）

### 5.1 成本来源

YR 的战术渲染是 **8 个图层各自遍历一遍 ViewBounds**（地面、地形物件、单位、动画、覆盖层等），每格每层都是一次独立的小 blit。所以开销随的是 **blit 调用次数**，而不是单纯的像素量 —— 小 blit 的固定开销比内存拷贝大得多。放大 ViewBounds 时，8 层一起放大。

最终上屏那一次是**恒定成本**（输出永远是 `W×H`），不随 `z` 变化，所以缩放 blit 本身不是瓶颈。

### 5.2 实测推算（1112×720 战术区）

cell 数 = `(W/z)/60 + 4` × `(H/z)/15 + 17`，常数项让实际倍数低于 `1/z²`：

| `z` | 视野跨度 | 列×行 | cell 数 | 相对原版 | 表面尺寸 | 表面内存 |
|---|---|---|---|---|---|---|
| 1.0 | 1112×720 | 22×65 | 1430 | 1.00x | 1.0W | 6.4 MB |
| 0.8 | 1390×900 | 27×77 | 2079 | 1.45x | 1.25W | 10 MB |
| **0.66** | **1685×1091** | **32×89** | **2848** | **1.99x** | **1.5W** | **14.4 MB** |
| 0.5 | 2224×1440 | 41×113 | 4633 | 3.24x | 2.0W | 25.6 MB |

（表面内存 = Composite + Tile 两者之和，`W×H×4B` 计）

### 5.3 为什么卡在 0.66

1. **面积正好翻倍**：`2.0x` cell 数，落在"能感觉到但可玩"的边界上。
2. **表面从 4 倍降到 2.25 倍**：`0.66 ≈ 2/3` ⇒ `W/z = 1.5W`。表面内存和每帧清屏是**恒定开销**，不管当前缩到多少都要付，所以降这一项比降 `z` 本身更值钱。
3. **再往下收益递减**：从 0.66 到 0.5，视野边长只多 33%（1.5W → 2.0W），cell 数多 62%，内存多 78% —— 花 60% 的性能换 33% 的视野，不划算；而且视野很大时"多看一眼"的边际价值在下降。
4. **离 clamp 红线有近一倍余量**：60 格地图、1112 宽下约 `z ≈ 0.36` 才会 `min > max` 钉边。

> 0.66 是"面积翻倍 + 表面 1.5 倍"这个目标**反推**出来的值，不是逆向得到的硬指标。做成可配置档：`0.5`（性能好）/ `0.66`（默认）/ `0.8`（保守）。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 表面尺寸固定为 `1.5W×1.5H` 的假设不成立 | M2 无法按预期零分配 | M0 第 1 项专门验证；不成立则退回"缩放时重建 Z/ABuffer"（更重但在 `Set_View_Dimensions` 能力范围内） |
| ZBuffer/ABuffer 索引越界 | **写坏堆、随机崩溃** | M0 必须验证；这条是整个方案里最危险的一处 |
| 相机 clamp 把画面吸边 | 缩小后无法居中 | 缩放帧事后覆盖中心；`z` 下限 0.66 |
| Tile/Composite 尺寸不一致 | 每帧交换 + 1:1 拷贝错位 | 两者永远同尺寸，一起重建 |
| 上屏走软件路径 | 不拉伸、花屏 | `dwUnk = 0` 强制硬件 Blt；M0 验证驱动是否硬件缩放 |
| 每帧按整幅清屏 | 表面放大后带来恒定开销，`z=1` 也变慢 | M0 第 2 项验证；必要时改成只清 `ViewBounds` |
| 与 ReShade / cnc-ddraw / dgVoodoo2 冲突 | 后处理失效或花屏 | 不动 Primary 尺寸、不 hook `Present`/`Flip`；只改 Primary 之前的合成，后处理层看不到，天然隔离 |
| 点击/框选偏移 | 点不中单位 | 拾取逆变换作为 M2 硬验收项，含 3 个 `sub_6D2280` 直连路径 |
| 掉帧 | 操作手感 | 成本按"blit 调用次数"涨（8 个图层各遍历一遍），`z=0.66` 约 2 倍、`z=0.5` 约 3.2 倍；`z=1` 时零开销，详见第 5 节 |
| 放大画质 | 像素块 | 放大本质是 upscale，无解（除非改投影矩阵，风险更高）；`z` 上限控制在 2.0 |
| 与 WDT 过场冲突（`+0xC0`） | 过场动画异常 | 我们强制 `+0xC0 = 1.0`，与 WDT 写入同一字段，只在该类地图出现，接受 |
| 分辨率变化 | 表面尺寸失配 | 监听显示设置变化后重建表面并复位 `z` |
| 联机安全 | — | 纯本地显示变换；相机中心是本地视图状态，不上网；拾取最终仍输出世界坐标，语义等价 |
| 录像回放 | 观感 | 显示层变换，不影响回放数据 |
